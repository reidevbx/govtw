# 模式決定表（2026-10-14）

把散在元件文件裡的組合用法，整理成 7 頁模式。使用者確認後依序連續執行，不再逐項詢問。

- 每項附建議做法；使用者只需改不同意的項目
- GOV.UK 模式清單與內容已於 2026-10-14 查證：https://design-system.service.gov.uk/patterns/
- 標「⚠️」的項目和現有元件或文件的做法不同，請特別確認

## 共通

| # | 問題 | 建議 |
|---|---|---|
| PA1 | 模式頁的結構 | 概述 → 何時使用 → 範例 → 做法（逐步說明） → 無障礙 → 用到的元件 → 參考來源。和元件頁不同，沒有屬性表 |
| PA2 | 側欄分組 | 「模式」底下分 2 組，參考 GOV.UK 的分法：**協助使用者**（表單錯誤處理、確認手機號碼、登入）、**頁面**（多步驟表單、完成頁、搜尋結果頁、長篇內容頁） |
| PA3 | 範例怎麼做 | 用 `<DemoBlock variant>` 組合既有元件，呈現一整頁或一個區塊。範例是靜態畫面，沒有後端，送出按鈕不會真的送出 |
| PA4 | 範例要不要有獨立預覽頁 | **要**。模式範例多半是整頁，獨立預覽比較看得清楚。需修改 2 個檔案：<br>• `scripts/build-previews.mjs`：同時掃 `patterns/`，產出到 `preview/patterns/<name>/`<br>• `DemoBlock.vue`：網址判斷加上 `/patterns/` |
| PA5 | 元件文件的組合用法 | 搬到模式頁。元件文件只留一句話加連結，同一段說明不寫兩次 |
| PA6 | `patterns/index.md` | 改成 7 個模式的清單，每項一句說明。移除「麵包屑導覽」「側邊欄導覽」「頁尾連結」，這三個已是元件 |
| PA7 | 參考來源怎麼寫 | 有 GOV.UK 對應模式的，附連結。沒有的，寫「台灣政府網站調查」，並說明 GOV.UK 為何沒有 |

## 協助使用者

### 表單錯誤處理（對應 GOV.UK Recover from validation errors）

| # | 問題 | 建議 |
|---|---|---|
| VA1 | 何時驗證 | 按下送出時才驗證。不在離開欄位時驗證，也不在輸入時驗證（GOV.UK 原文：「Do not validate when the user moves away from a field」） |
| VA2 | 錯誤時的頁面 | 重新顯示同一頁，保留使用者已填的內容。頁首放 error-summary 並移入焦點，每個錯誤欄位設 `error`，`<title>` 前加「錯誤：」 |
| VA3 | HTML5 驗證 | `<form>` 加 `novalidate`，欄位不加 `required`，改用伺服器驗證。前端驗證是選配，規則要和伺服器一致 |
| VA4 | 範例 | 一個表單，2 個欄位出錯，頁首有錯誤摘要 |
| VA5 | 元件文件 | error-summary 文件的「頁面標題加錯誤：」搬到這頁，原處留連結 |

### 確認手機號碼（對應 GOV.UK Confirm a phone number）

| # | 問題 | 建議 |
|---|---|---|
| CP1 | 範圍 | **只寫手機**。GOV.UK 把 Email 拆成另一個模式（Confirm an email address），我還沒讀它的內容，留到後續 |
| CP2 ⚠️ | 重新傳送的做法 | GOV.UK 的做法：輸入頁放「沒收到簡訊？」連結，連到另一頁，再按「重新傳送」。我們的 otp-input 是在同一頁放倒數按鈕。**建議保留 otp-input 的做法**，模式頁說明兩者差異：同頁按鈕少換一次頁，但需要 JavaScript |
| CP3 ⚠️ | 是否顯示手機號碼 | GOV.UK：註冊時顯示號碼，並讓使用者修改；**登入時不顯示號碼**。otp-input 的範例在提示裡寫了遮蔽後的號碼。建議把它改成註冊情境，並加上「修改手機號碼」連結 |
| CP4 | 驗證碼期限 | 文件寫：重新傳送後舊驗證碼在原期限內仍有效。GOV.UK 用 15 分鐘，我們不規定秒數，由機關決定，寫在提示裡 |
| CP5 | 錯誤訊息 | 分成 4 種情況：驗證碼錯誤、已過期（同時自動重新傳送）、位數不足、位數過多。例如「驗證碼已過期，已重新傳送」 |
| CP6 | 防止暴力嘗試 | 文件寫：連續輸錯 10 次後延遲才能再試（GOV.UK 的建議）。這是伺服器的工作，元件不處理 |

### 登入（GOV.UK 沒有對應模式）

| # | 問題 | 建議 |
|---|---|---|
| SI1 | 內容 | 帳號（text-input，`autocomplete="username"`）、password-input、送出按鈕。加上「忘記密碼」連結 |
| SI2 | 圖形驗證碼 | 把 captcha 文件的 WCAG 3.3.8 說明搬到這頁：用了圖形驗證碼，就要另外提供不用驗證碼的登入方式 |
| SI3 | 登入失敗的訊息 | 寫「帳號或密碼錯誤」，不指出是哪一項錯。這是常見的資安做法，不是 GOV.UK 的規範，文件會註明來源是資安慣例 |
| SI4 | 數位憑證、行動自然人憑證登入 | 只提到可以作為替代登入方式，不寫流程。各機關的實作不同，我沒有查證 |

## 頁面

### 多步驟表單（對應 GOV.UK Question pages、Check answers）

| # | 問題 | 建議 |
|---|---|---|
| MS1 | 一頁幾題 | 一頁只問一件事（GOV.UK 的做法），例外是彼此相關的欄位，如地址 |
| MS2 | 頁面組成 | back-link → step-indicator（或「第 x 步，共 n 步」文字）→ 標題（問題本身）→ 欄位 → 「繼續」按鈕 |
| MS3 | 最後一步 | 用 summary-list 列出所有答案，每項有「修改」連結，確認後才送出。把 GOV.UK 的 Check answers 併進這頁 |
| MS4 | 範例 | 2 個：中間某一步、最後的確認頁 |

### 完成頁（對應 GOV.UK Confirmation pages）

| # | 問題 | 建議 |
|---|---|---|
| CF1 | 頁面組成 | panel（標題加案件編號）→ 接下來會發生什麼事 → 聯絡方式 → 意見回饋連結 |
| CF2 | 案件編號 | 放在 panel 裡，文件建議同時寄 Email 或簡訊給使用者 |

### 搜尋結果頁（GOV.UK 沒有對應模式）

| # | 問題 | 建議 |
|---|---|---|
| SR1 | 頁面組成 | search（保留關鍵字）→「共 N 筆」→ 每頁筆數 → document-list → pagination |
| SR2 | 沒有結果時 | 寫「找不到符合『關鍵字』的結果」，並提供建議：檢查錯字、換關鍵字 |
| SR3 | 元件文件 | pagination 文件的「結果筆數與每頁筆數」範例搬到這頁，原處留連結 |
| SR4 | 篩選條件 | **不寫**。篩選介面需要另外設計，留到後續 |

### 長篇內容頁（GOV.UK 沒有對應模式）

| # | 問題 | 建議 |
|---|---|---|
| LC1 | 頁面組成 | sidebar 佈局：左側 side-navigation；主內容依序為 h1 → contents-list → 內文 → attachment → page-tools |
| LC2 | 何時拆頁 | 文件建議：使用者通常只看其中一段時，考慮拆成多頁，而不是用目錄撐住一頁 |
